# Discord Bot Assistant for Collaborative Research Environments

Bachelor thesis project developed in Python using `discord.py`.

The project provides a modular Discord bot designed to support collaborative research environments.
The current implementation focuses primarily on **service monitoring**, allowing configured services to be checked manually and automatically, with status tracking, Discord alerts, and persistent monitoring history.

> **Development status:** active development.
> The current monitoring subsystem is implemented and functional. Additional features may be added after further alignment on the final thesis scope.

---

## Current Features

The bot currently supports:

* Modular Discord bot architecture based on Cogs.
* Manual service status checks through `/status`.
* Configurable monitored services.
* HTTP-based availability checks.
* Periodic automatic monitoring.
* Service states:

  * `UP`
  * `DOWN`
  * `ERROR`
* Runtime tracking of the latest service state.
* Detection of status transitions.
* Automatic Discord notifications when a service changes state.
* Recovery notifications when a service becomes available again.
* Support for multiple Discord alert destinations.
* Persistent monitoring history using JSON Lines files.
* Persistent history of service state transitions.
* `/history` command for inspecting recent monitoring results.
* Structured application logging.
* Automated tests for the main monitoring components.

Manual `/status` requests are intentionally kept separate from automatic monitoring and are not stored in monitoring history.

```text
│

├── pytest.ini

```

The main responsibilities are separated into different components:

* `cogs/`: Discord-facing commands and interactions.
* `monitoring/`: service definitions, checks, scheduling, state tracking and transition detection.
* `alerts/`: outgoing notifications generated by monitoring events.
* `history/`: persistent storage and retrieval of monitoring history.
* `resources/`: configurable services and runtime behaviour.

This separation is intended to keep the monitoring logic independent from Discord-specific functionality and to make future extensions easier.

## Service Configuration

Monitored services are configured in:

```text
resources/services.json
```

Example:

```json
{
  "services": [
    {
      "key": "unimore",
      "display_name": "UniMORE Website",
      "checks": [
        {
          "type": "http",
          "name": "Website availability",
          "url": "https://www.unimore.it/",
          "expected_status": 200,
          "timeout_seconds": 5.0
        }
      ]
    }
  ]
}
```

A service represents something that should be monitored, while each check defines how its availability is verified.

The current implementation provides HTTP checks. The architecture is designed to allow additional check types to be introduced later without changing the Discord commands or the monitoring scheduler.

## Runtime Configuration

Runtime behaviour is configured in:

```text
resources/runtime.json
```

Example:

```json
{
  "monitoring": {
    "interval_seconds": 60
  },
  "history": {
    "enabled": true,
    "directory": "data/history"
  },
  "alerts": {
    "discord": {
      "enabled": true,
      "destinations": [
        {
          "name": "development",
          "guild_id": "YOUR_GUILD_ID",
          "channel_id": "YOUR_CHANNEL_ID"
        }
      ]
    }
  }
}
```

This configuration controls:

* automatic monitoring interval;
* monitoring history;
* history storage location;
* Discord alerts;
* Discord destinations receiving transition notifications.

Multiple Discord destinations can be configured.

## Discord Commands

### `/ping`

Checks whether the bot is responsive and displays its current Discord latency.

### `/about`

Displays general information about the project and bot.

### `/status`

Runs a manual monitoring check for a selected service.

Example:

```text
/status service:unimore
```

Manual checks do not modify the automatic monitoring state and are not stored in monitoring history.

### `/history`

Displays recent automatically collected monitoring results for a selected service.

Example:

```text
/history service:unimore limit:5
```

The command can also display recent status transitions when available.

## Automatic Monitoring

The monitoring scheduler periodically checks all configured services.

A typical monitoring flow is:

```text
Configured Service
       ↓
Monitoring Check
       ↓
Service Result
       ↓
Persistent History
       ↓
Runtime State
       ↓
Transition Detection
       ↓
Discord Alert
```

The first result observed after startup establishes the initial state and does not generate a transition alert.

For example:

```text
Initial state → UP       no alert
UP → UP                  no alert
UP → DOWN                alert
DOWN → DOWN              no additional alert
DOWN → UP                recovery alert
```

This prevents repeated notifications while a service remains in the same state.

## Monitoring History

Automatic monitoring results are stored using JSON Lines (`.jsonl`) files.

By default:

```text
data/
└── history/
    ├── service_results.jsonl
    └── transitions.jsonl
```

`service_results.jsonl` contains the results produced by periodic monitoring, including the individual checks associated with each service.

`transitions.jsonl` contains significant service state changes such as:

```text
UP → DOWN
DOWN → UP
UP → ERROR
```

The history layer is kept separate from the monitoring logic so that the storage implementation can be replaced in the future if necessary.

Generated history files are runtime data and are not committed to Git.

## Logging

Application logs are written both to the console and to rotating log files.

Generated logs are stored under:

```text
logs/
```

Logging includes contextual information such as the service and check involved in monitoring operations.

Failures in optional components such as history persistence or Discord notifications are isolated where possible so that they do not stop the monitoring scheduler.
